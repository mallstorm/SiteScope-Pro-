# Аудит SiteScope Pro (beta12) и план исправлений

Дата: 2026-11-13. Ветка `redesign`. Метод: статический разбор кода и документации, CI (тесты + Lint). Запуск на физическом устройстве в этом аудите **не выполнялся**.

## 0. Правки Codex (beta13–beta23): появились в `redesign` во время аудита

Первый проход (до обновления ветки) этих коммитов не видел; затем они были запушены и разобраны. Объём: ~100 файлов — карточки устройств и история измерений, отпечатки HTTP/TLS/ONVIF, отчёты CSV/JSON/HTML, чтение DHCP/ARP с **собственных** роутеров RouterOS/OpenWrt по API, сравнение снимков, смена имени роутера с журналом отката, внешние TCP-измерения, перемотка ТВ, ONVIF/RTSP-сессии, регулировка 2–250 потоков и «IPTV без лимита хостов».

Вывод по соответствию заявленной цели: это **не** перенос RouterScan (нет подбора паролей, нет эксплуатации чужих устройств, нет сбора учётных данных). Все операции с роутером идут по учётным данным владельца, фиксированным набором вызовов; логин/пароль лежат в `SecureStore` и привязаны к адресу и типу адаптера; запись имени роутера защищена предпросмотром (срок 120 с), проверкой «значение не изменилось», журналом до записи и проверкой результата; отчёты вычищают пароли/токены (`ReportText`). Это верное направление, совпадающее с `docs/08_AUTHORIZED_SCANNER_RU.md`. Функции RouterScan по подбору паролей и извлечению учётных данных чужих роутеров не добавлялись и не должны добавляться.

## 2. Что добавлено в beta26

- **Скорость как в Ookla Speedtest** (`net/SpeedEngine.kt`, `SpeedScreen.kt`): спидометр с нелинейной шкалой, задержка/джиттер/потери, задержка под нагрузкой, скачивание и отдача в несколько потоков с «живой» скоростью, пик, серверы (Cloudflare, Tele2, Hetzner, OVH, свой), настройки (что измерять, единицы Мбит/с · МБ/с · кбит/с, длительность, потоки, число пингов, лимит трафика), история и «поделиться». Старая проверка «скачать/отправить файл» удалена.
- **Поиск потоков по маске** (`tv/MaskSearch.kt`, `MaskSearchScreen.kt`): `%d`, `%d{a-b}`, `%03d`, `(a|b|c)`, `(.*)`, `channel_name`, `xxx.xxx.xxx.xxx`, `yyyyy`; перебор с лимитом, параллельностью, быстрой отсечкой мёртвых host:port; http/https — полная проверка потока, rtsp — DESCRIBE, rtmp/mms — проверка порта. Окно вверху: квадрат с кадром из потока (или логотип из ваших каналов) и распознанное название. Название берётся из служебных таблиц потока (SDT), затем читается с эмблемы (OCR), затем из маски; известные каналы приводятся к виду «1+1», «Интер», «НТВ», «РЕН ТВ». Вход: «Ещё → Поиск ТВ по маске», раздел «ТВ в локальной сети» и «Добавить плейлист».
- Тесты: `MaskSearchTest` (перебор, диапазоны, нули, альтернативы, `(.*)`, названия, IP/порты, распознавание).

## 3. Ограничения (честно)

- Название по эмблеме читает Tesseract (язык rus: кириллица, латиница, цифры, `+`; данные `rus.traineddata` ≈3,9 МБ в assets, библиотека Tesseract4Android 4.9.0 с JitPack, только arm64). Читаются четыре угла до трёх кадров, снятых в случайные моменты; известные каналы принимаются с одной опечаткой, произвольный текст — только при двух совпадающих уверенных чтениях. Если эмблема не видна — «Нет названия». Украинские буквы і/ї/є модель rus не знает (читаются как и/и/е); добавить `ukr` — ещё ≈3,8 МБ. Точность на реальных потоках не измерена (устройства не было): кадр с титрами или без эмблемы названия не даст.
- `udp://@группа:порт` проверяется подпиской на мультикаст-группу (`MulticastProbe`: не более 3 групп одновременно, молчащая группа ждёт до таймаута, до 2 МБ потока для названия из SDT и кадров); работает только в сети, где идёт мультикаст. `rtp://` пока пропускается (следующий шаг).
- Серверы Tele2/Hetzner/OVH — публичные тестовые файлы; их доступность не гарантируется (Cloudflare — основной).
- Сборка и тесты проверяются только в CI; устройства для проверки не было.

## 5. beta29: встроенный браузер, Onion и I2P

**Причины «пустой страницы роутера»** (`WebClientActivity`): не было `onReceivedHttpAuthRequest`, поэтому запрос Basic/Digest отменялся молча; не было диалогов `alert/confirm/prompt` (панели роутеров на них держатся), выбора файла, загрузок и страниц ошибок; `MIXED_CONTENT_NEVER_ALLOW` ломал ресурсы; UA содержал `wv`. Всё добавлено; пароль можно сохранить в `SecureStore` (AES в Android Keystore).

**Onion/I2P** (`pro.sitescope.app.anon`): локальный HTTP-прокси на 127.0.0.1 (`AnonProxy`) выбирает путь по имени узла: `*.onion` → Tor по SOCKS5 с удалённым DNS, `*.i2p` → HTTP-прокси или SOCKS I2P, остальное напрямую (или через Tor в режиме «весь трафик», кроме LAN). WebView подключается через `androidx.webkit.ProxyController`. Если Tor/I2P недоступны, запрос завершается страницей 502 и никогда не уходит в обход. Tor — встроенный (`info.guardianproject:tor-android`) или внешний (Orbot 9050 / Tor Browser 9150).

**Ограничения:** I2P-роутер во встроенном виде невозможен (нет библиотеки для Android) — нужен I2P/i2pd; WebView не даёт анонимности уровня Tor Browser (отпечаток браузера, JS); Tor может быть заблокирован провайдером (нужны мосты через Orbot); `TorService` не является foreground-сервисом и может быть остановлен системой в фоне; прокси слушает только loopback, но доступен другим приложениям устройства; работа на устройстве не проверялась — покрыто тестами маршрутизации и SOCKS5 на JVM.

## 6. beta30: обход блокировок (DPI)

**Движок.** Вшит исходный код byedpi (hufrea, лицензия MIT, `app/src/main/cpp/byedpi`, коммит указан в `UPSTREAM_COMMIT`). Gradle-задача `buildCiadpi` собирает его NDK-clang в исполняемый файл `libciadpi_exec.so` (arm64, PIE, страницы 16 КБ), который запускается отдельным процессом из `nativeLibraryDir`. Падение движка не роняет приложение; супервизор перезапускает его (не чаще 5 раз в минуту). Ключи `-i/-p/-D/-w/-E/-y/-h/-v` вычищаются из пользовательской строки, адрес и порт задаёт приложение.

**Три способа использования.**
1. *Прокси без VPN* — фоновый сервис держит SOCKS5 `127.0.0.1:порт`. VPN-слот свободен, работает параллельно с любым VPN. Подходит приложениям с настройкой прокси (Telegram) и встроенному браузеру SiteScope. Принудительно направить в прокси произвольное приложение без VPN Android не позволяет.
2. *VPN с обходом* — собственная служба VPN + HEV tun2socks → byedpi. Режимы: все приложения, только выбранные, все кроме выбранных.
3. *Внутри VPN SiteScope* — исходящие соединения Xray идут через byedpi (`sockopt.dialerProxy`). Экспериментально.

Android допускает один активный VPN: при конфликте с VPN SiteScope предлагается остановить его или включить режим 3.

**Подбор.** Сначала проверка без обхода (какие сайты реально недоступны), затем параллельный быстрый прогон стратегий на нескольких портах, затем полная проверка лучших. Проверка — TLS с проверкой сертификата и имени, обрезанные ответы считаются неудачей. Контрольные сайты (wikipedia, microsoft, apple) отсекают стратегии, ломающие обычный трафик. Подбор требует выключенного VPN.

**Ограничения.** Не проверялось на устройстве в рамках сборки: нужна проверка на реальном провайдере. Десинхронизация зависит от провайдера, стратегию надо подбирать для каждой сети. Только arm64. Дочерний процесс может быть остановлен системой на агрессивных прошивках (держите уведомление сервиса и исключите приложение из оптимизации батареи).

**Благодарности.** ByeByeDPI и byedpi (hufrea), подходы zapret (bol-van).

## 7. beta31: встроенные Tor и I2P (по образцу RouteMatrix PRO 4.2)

**Что нашлось в архивах.** В RouteMatrix PRO 1.0.0-pro.4.2 Tor запускается как отдельный исполняемый файл `libtor.so` со своим `torrc`, а i2pd — как официальная JNI-библиотека PurpleI2P в отдельном процессе `:I2PCore`; готовность I2P определяется по журналу (построены входящий и исходящий туннели) и открытому HTTP-прокси. В L2Ray 2.5.2 i2pd запускался как обычный исполняемый файл, но `libi2pd.so` — это JNI-библиотека без точки входа, так что та ветка рабочей не была. Бинарные файлы в обоих архивах совпадают.

**Что сделано в SiteScope.**
- *Tor:* встроенный Tor Guardian Project заменён процессом `libtor.so` (0.4.9.5) с собственным `torrc` (`ClientOnly`, `IsolateSOCKSAuth`, без ControlPort). Порт выбирается свободный. Разбор `Bootstrapped N%`, классификация сбоев (часы, сеть, TLS-блокировка, каталог, таймаут, прокси), сторожевой таймер на 180 с. Способ выхода: напрямую / через byedpi / через заданный SOCKS5 (`Socks5Proxy`) / «Авто» — сначала напрямую, при остановке на ранней стадии (≤15% за 45 с) один раз переключение на byedpi. Простые мосты `IP:порт [отпечаток]`; obfs4/snowflake/webtunnel отфильтровываются с пояснением (клиента подключаемых транспортов в сборке нет). Кнопка «Проверить» запрашивает check.torproject.org через Tor.
- *I2P:* встроенный i2pd 2.60.0 в процессе `:i2pcore`. Конфиг: `notransit`, NTCP2 и SSU2 без публикации, веб-консоль/SAM/BOB/I2CP выключены, HTTP-прокси `127.0.0.1:14444`, SOCKS `127.0.0.1:14447` (при занятости — свободные порты). Список узлов (reseed) при недоступных серверах берётся через byedpi (`reseed.proxy`), через SOCKS5, из локального `.su3` или по HTTPS-адресу. В режиме «Авто» при ошибках reseed ≥60 с приложение само перезапускает I2P с обходом DPI. После остановки процесс `:i2pcore` завершается, чтобы следующий запуск был чистым. Данные (netDb) сохраняются между запусками — повторные старты быстрые.
- *Браузер:* статус-страница показывает прогресс, число туннелей и подсказку про первый запуск; ожидание I2P до 8 минут, Tor до 5.
- *Служебное:* общий `AnonDpi` поднимает byedpi по требованию и гасит, когда он больше никому не нужен (сервис пользователя не затрагивается); `App.onCreate` в `:i2pcore` ничего лишнего не инициализирует.

**Не проверено на устройстве.** Запуск обоих движков, реальный reseed через byedpi и открытие сайтов I2P проверить в сборке нельзя: в CI выполняются только компиляция и юнит-тесты (конфигурации, классификатор, планировщик, разбор журналов). Бинарные файлы взяты из предоставленных архивов, не из исходников (см. `third_party/anon/NOTICE.md`).
