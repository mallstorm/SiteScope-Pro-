# SEO: технологии сайта, DNS и доменная инфраструктура

Версия: 0.29.0-alpha27

## 1. Назначение

Модуль дополняет обычный SEO-аудит технической разведкой домена без активного сканирования административных панелей, перебора путей и платных API. Анализ выполняется только по уже полученному HTML, HTTP-заголовкам, cookies, публичным DNS-записям, RDAP и RIPEstat.

## 2. Определение CMS и технологий

Каждая технология описывается четырьмя полями:

- название;
- категория;
- уверенность 0–99%;
- список доказательств.

Сигналы имеют разный вес. Например, `meta generator=WordPress` сильнее случайного упоминания `wordpress` в тексте. Несколько независимых признаков суммируются. CMS показывается как определённая только при наличии достаточных доказательств.

Проверяются:

- meta generator;
- пути JavaScript/CSS и API;
- cookies;
- Server и X-Powered-By;
- характерные HTML-атрибуты;
- CDN/WAF и аналитические скрипты.

Активные запросы к `/admin`, `/wp-admin`, `/administrator` и подобным адресам не выполняются.

## 3. DNS-анализ

Для фактического host запрашиваются:

- A;
- AAAA;
- CNAME.

Для корневого регистрируемого домена запрашиваются:

- MX;
- NS;
- TXT;
- SOA;
- CAA;
- DNSKEY;
- DS;
- распространённые SRV-записи;
- `_dmarc` TXT.

Каждая строка отчёта содержит имя, тип, значение и TTL.

### Транспорт

1. Обычный DNS UDP/53.
2. При блокировке UDP — DNS-over-HTTPS Cloudflare.
3. При недоступности Cloudflare — DNS-over-HTTPS Google.

Ключевые A/AAAA/NS ответы дополнительно сравниваются между Cloudflare и Google. Если проверку нельзя завершить в ограниченный таймаут, приложение не утверждает согласованность.

## 4. Почтовая безопасность

- SPF определяется по `v=spf1`.
- DMARC определяется по `_dmarc` и `v=DMARC1`.
- DKIM требует selector, поэтому без известного selector приложение не делает ложный вывод.
- Если MX отсутствует, отсутствие SPF/DMARC не маркируется как ошибка почтового домена.

## 5. DNSSEC и CAA

DNSSEC в этом релизе означает наличие одного из публичных признаков:

- DNSKEY;
- DS;
- authenticated-data flag от резолвера.

Это не заменяет полноценную локальную проверку RRSIG по цепочке доверия. Формулировка интерфейса специально не заявляет полную криптографическую валидацию.

CAA является рекомендуемой, но необязательной записью. Её отсутствие отображается нейтрально.

## 6. RDAP и сеть

RDAP возвращает:

- регистратора;
- дату создания;
- дату окончания;
- статусы домена;
- nameservers.

По первому IP выполняется облегчённая RIPEstat-сводка:

- prefix;
- ASN;
- владелец/holder;
- reverse DNS.

Полный WHOIS, abuse-контакты и геокаталоги остаются в отдельном IP Intelligence и не дублируются в SEO.

## 7. Хранение

Результат сохраняется внутри `AuditResult`:

- CMS и уверенность;
- список технологий;
- DNS-записи;
- статусы SPF/DMARC/DNSSEC/CAA;
- RDAP;
- ASN и reverse DNS.

Исторический отчёт открывается из SQLite без повторного сетевого анализа. Старые отчёты остаются совместимыми: новые поля для них отображаются как «не проверено».

## 8. Ограничения

- Скрытые или сильно модифицированные CMS могут не определиться.
- Версия CMS не утверждается без надёжной сигнатуры.
- RDAP и RIPEstat зависят от доступности внешних публичных сервисов.
- DNS-over-HTTPS требует работающего системного DNS для разрешения адреса DoH-провайдера; при полном отказе DNS остаётся прямой UDP-запрос по IP резолвера.
- Реальный сетевой тест следует выполнить на Android-устройстве в Wi-Fi и мобильной сети.
