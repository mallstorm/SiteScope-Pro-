# Центр камеры — этап 5, beta18

## Путь пользователя

«Моя сеть → Устройства → карточка → Камера: профили и видео» открывает единый экран камеры. Также он доступен из сохранённого ONVIF-подключения. Введите данные владельца, при необходимости исправьте путь и порт device service, получите сведения и выберите видеопрофиль. «Адрес» копирует RTSP-ссылку без добавленного логина/пароля; «Смотреть» открывает встроенный плеер.

Статусы различаются: объявление устройства в discovery, получение сведений/профилей ONVIF, получение адреса RTSP и фактический запуск потока. Полученный URI не выдаётся за подтверждение воспроизведения. Пустой список профилей отображается отдельно от ошибки авторизации. Ошибки HTTP/SOAP не выводят в интерфейс содержимое ответа камеры.

## Реализация

- Прежние Java/Kotlin реализации ONVIF заменены общим `CameraClient`. Старый Activity перенаправляет на основной экран.
- Поддерживаются Media1 и Media2. Media1 ищется в стандартном атрибуте XAddr Media в GetCapabilities (также принимается отдельный элемент XAddr); при отсутствии media-сервиса используется GetServices с выбором точного пространства имён Media1/Media2. Чужой XAddr не выбирается как запасной media-сервис.
- GetDeviceInformation допускает ответ «операция не поддерживается»; это не мешает получить профили. Производитель/модель разбираются общим движком признаков. Новые данные этого экрана показываются в текущем сеансе; опрос не изменяет конфигурацию камеры.
- Используется WS-Security UsernameToken PasswordDigest с новым nonce и UTC-временем на запрос. Для HTTP Digest поддержаны MD5/SHA-256 и их sess-варианты, qop=auth или legacy без qop; после challenge допускается одна повторная попытка на тот же адрес. Автоматического перехода к Basic нет. Неверные данные, неподдерживаемая схема авторизации и несовпадающее время камеры могут потребовать настройки на стороне владельца.
- Сетевые запросы выполняются вне UI-потока. Один активный запрос на экран; повторные нажатия блокируются. «Отменить», уход с экрана и уничтожение экрана отменяют ожидание и закрывают соединение; поздние ответы не изменяют новый сеанс. Отмена интерфейса не зависит от скорости завершения системного сетевого вызова.
- Таймаут отдельного соединения/чтения — до 8 секунд; бюджет опроса 25 секунд, получения URI — 12 секунд, проверяется между сетевыми операциями и порциями ответа. Системный блокирующий вызов может завершиться позже до своего таймаута. Ответ ограничен 512 КиБ, глубина/число XML-узлов и размер текстовых значений ограничены. DTD/ENTITY отклоняются; SOAP Body, операция и пространства имён проверяются.

## Адреса, сеть и данные входа

Адрес device service привязан к выбранному хосту камеры. Путь и порт можно изменить; для другого IP/имени нужно открыть соответствующее подключение. Это сохраняет правильную привязку сохранённых учётных данных. При объявленном Media XAddr разрешён другой порт того же хоста; чужой хост, HTTP-редирект и понижение HTTPS до HTTP не используются. Для HTTPS действует системная проверка сертификата. Объявленные 0.0.0.0/:: заменяются адресом выбранной камеры. Синонимы DNS и IP автоматически не считаются одним хостом: для камеры с некорректной рекламой адресов используйте её прямой адрес.

RTSP URI проверяется на протокол и соответствие хосту. Встроенные в объявленную ссылку логин/пароль отбрасываются; для просмотра используются данные, введённые пользователем. Проприетарные способы авторизации и RTSPS этим выпуском не добавляются.

ONVIF привязан к выбранному Android Network. Сохраняется LAN-область исходного обнаружения; для числового адреса учитывается подходящий локальный маршрут, даже если по умолчанию выбрана мобильная сеть. При активном VPN без исходной LAN-привязки сохраняется маршрут VPN. Если между опросом и получением URI сеть изменилась, нужно повторить опрос. Выбранная сеть передаётся плееру только через сессию в памяти; RTSP TCP-сокеты используют её SocketFactory.

Для запуска видео передаётся случайный одноразовый токен, а не URL с паролем. Сессии находятся только в памяти, действительны две минуты до получения плеером (очистка просроченных записей выполняется при обращении к хранилищу сессий), ограничены восемью ожидающими запусками. После получения токен удаляется. Intent содержит токен и имя профиля; общий журнал подключений не получает данные RTSP-авторизации. Сам плеер использует URL с данными входа только в памяти. Потеря процесса/истечение токена требует повторно открыть профиль. Это не обещание мгновенного затирания строк в памяти JVM.

«Запомнить на этом телефоне» использует существующий SecureStore по явному выбору пользователя. Это отдельное защищённое хранение, которое не входит в переносимую копию. Экран не сохраняет разрешённый RTSP URL в плейлист.

## Воспроизведение

Media3 использует RTSP поверх TCP, таймаут 8 секунд и ограничение начального ожидания 20 секунд. Ошибка RTSP больше не запускает попытку HLS/MPEG-TS для той же ссылки. Авторизация, сеть/таймаут и неподдерживаемый кодек получают разные сообщения. Поток камеры останавливается при уходе плеера в фон без PiP и заново открывается при возвращении. При закрытии Activity плеер освобождается. Предпочтение TCP помогает сетям с фильтрацией UDP, но не гарантирует поддержку любого кодека и любой камеры.

## Проверки

Локальные сетевые фикстуры покрывают Media1/Media2, точность WS-Security digest, HTTP Digest, HTTP/SOAP авторизацию, редиректы и чужие адреса, пустые профили, некорректный XML, предел ответа, таймаут и отмену. Отдельно проверяются одноразовые токены, срок/предел сессий, кодирование данных входа и отсутствие URL/пароля в Intent и журнале. Существующие проверки истории и карточек сохраняются.

Физический прогон ONVIF → профиль → Media3 RTSP на телефоне остаётся отдельным. В сессии нет подключённой физической камеры; успех HTTP/XML тестов не доказывает воспроизведение реального видеокодека.
